# F1–F5: sign-in, assigned-to-me, reviewed marking, update detection, update view

Status: built in 0.2.0; this is the specification it was built from (`docs/product-baseline.md` describes the result). Research date: 2026-10-20.
"Verified" means checked against the sandbox `igorvolokhovych/test-pr-reviewer` with read-only calls. Items marked **UNVERIFIED** come from docs or inference only.

Azure DevOps REST `api-version=7.1` unless noted. `{org}` = `https://dev.azure.com/{organization}`, `{vssps}` = `https://vssps.dev.azure.com/{organization}`, `{repo}` = `{org}/{project}/_apis/git/repositories/{repository}`.

## Shared: error states

Every feature maps HTTP outcomes the same way. The client already implements the 203 and `Retry-After` rows; the others are UI mapping.

| Condition | How it shows up | User-facing state | Action offered |
|---|---|---|---|
| PAT missing | no PAT in the password storage | Sign-in panel (F1) | Sign in |
| PAT rejected: wrong, expired or revoked | `401`, or `203` with an HTML sign-in page, or a redirect to sign-in. The docs only say "rejected"; the mapping is from community sources (**UNVERIFIED**) | "Azure DevOps rejected the token. It may have expired or been revoked." | Sign in again, Create token (link) |
| Missing scope or permission | `403` | "The token can't do this. It needs: Code (Read & write), Identity (Read), Graph (Read)." | Sign in again with a new token |
| Not found or no access | `404`. Azure DevOps uses it for both, so they can't be told apart | "Project, repository or pull request not found, or the token has no access to it." | Open settings, Retry |
| Throttled | `429`, or `Retry-After` on any response | "Azure DevOps is limiting requests; retrying in N s." The client waits for `Retry-After` and retries up to 3 times | Automatic, then Retry |
| Service error | `5xx` | "Azure DevOps is unavailable (HTTP 5xx)." | Retry |
| Network | connect or read timeout, DNS failure | "Can't reach dev.azure.com." | Retry |
| PAT expiry | can't be read in advance: the PAT lifecycle and profile APIs need an Entra token, not a PAT ([PAT docs](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/use-personal-access-tokens-to-authenticate?view=azure-devops)) | Shows as "PAT rejected" when it happens | Same as "PAT rejected" |

Error text never includes the PAT, the `Authorization` header or response bodies. It shows the HTTP status and the service's `message` field only. The client tests already enforce this.

## F1. Sign-in on first run

**User story.** As a reviewer opening the plugin for the first time, or after my token stopped working, I'm asked to sign in right away. I enter my token once, and I'm not asked again until it stops working.

**Flow**
1. **Trigger:**
   - the tool window is shown and there's no organization or PAT; or
   - any call returns "PAT rejected".

   There's no IDE-startup popup: the prompt appears where the user is looking.
2. **Sign-in panel**, replacing the tool window content:
   - Organization: prefilled from the Git remote when it is `dev.azure.com/{org}` or `ssh.dev.azure.com:v3/{org}/…`.
   - Personal access token: masked.
   - Required scopes, listed in the panel.
   - **Create token** link to `https://dev.azure.com/{org}/_usersSettings/tokens`.
   - **Sign in** button.
3. **Validate before saving.**
   - Call `GET {org}/_apis/connectionData`, which returns `authenticatedUser.id` and `providerDisplayName` (verified 200).
   - If a project and repository are configured, also call `GET {repo}` to check access to them.
4. **On success**, save the PAT in the IDE password storage (`PasswordSafe`, service name `Azure DevOps PR Review — {organization}`), store the user id in memory, and load the list.
5. **On failure**, keep the panel and show the shared error state inline with **Retry**. Nothing is saved.
6. **When a saved PAT is rejected:**
   - Discard the in-memory provider.
   - Show the panel again with the reason.
   - Keep the stored token until a new one validates, so a transient 401 can't wipe it.

**Acceptance criteria**
- AC1: With no PAT saved, opening the tool window shows the sign-in panel, not an empty list or a stack trace.
- AC2: A valid PAT signs in with one click, and the list loads without restarting the IDE.
- AC3: An invalid PAT shows "rejected" inline, and nothing is written to the password storage.
- AC4: The PAT never appears in settings XML, `idea.log`, exception messages or UI text.
- AC5: After a PAT is revoked, the next action shows the sign-in panel with the reason. Signing in again restores the view.
- AC6: Global (all-organizations) PATs stop working on 1 Dec 2026. The panel tells users to create an org-scoped token.

**State.** Organization: app-level settings. PAT: `PasswordSafe` only. Current user id: memory only, refreshed on sign-in.

**Test cases**
- Unit, fixture server:
  - `connectionData` 200 → signed in;
  - 401 → rejected;
  - 203 HTML → rejected;
  - 403 → scope message;
  - network error → offline message.
- Unit: the sign-in view model doesn't call `setPat` on failure, and calls it exactly once on success.
- Unit: Git remote parsing for `https://{org}@dev.azure.com/{org}/{project}/_git/{repo}`, `https://dev.azure.com/...` and `git@ssh.dev.azure.com:v3/{org}/{project}/{repo}`.
- Manual (sandbox-plan S1): no PAT, garbage PAT, valid PAT, a PAT revoked mid-session, and a PAT without Code scope.

## F2. "Assigned to me" view

**User story.** As a reviewer I see every active PR where I'm a reviewer, directly or through a team, with its status and my vote, so I know what to review.

**API**
- **Me:** `connectionData.authenticatedUser.id`, verified.
- **My teams:** `GET {org}/_apis/projects/{project}/teams?$mine=true`. Verified 200: 1 team, and the ids are GUIDs.
- **PRs:** `GET {repo}/pullrequests?searchCriteria.reviewerId={id}&searchCriteria.status=active`, run once for my id and once per team id, then de-duplicated by `pullRequestId`.
  - `reviewerId` does **not** expand group membership ([get-pull-requests](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/get-pull-requests?view=azure-devops-rest-7.1)), hence the per-team queries.
  - Verified: a team GUID is accepted as `reviewerId` (HTTP 200).
  - Whether a PR assigned only to the team is returned is **UNVERIFIED** until sandbox PR S2-C exists.
- **List data:** the list response already includes `reviewers[]` with `vote`, `isRequired`, `isFlagged` and `hasDeclined` (`IdentityRefWithVote`), plus `lastMergeSourceCommit` (verified in the recorded fixture). No per-PR call is needed.

**Shown per PR**
- id, title, author, branches, draft badge.
- **My role:** required or optional reviewer, or "via team {name}".
- **My vote:** Approved, Approved with suggestions, Waiting for author, Rejected, or No vote. For a team-only assignment, show the team's vote (`votedFor` roll-up).
- **Review state** from F3/F4: Needs review, Reviewed, or Updated since review.

**Rules**
- **Default sort:** Needs review, then Updated since review, then Reviewed; newest first within each group.
- **Declined PRs:** where I have `hasDeclined = true`, the PR is hidden by default, with a "Show declined" toggle (open decision D23).
- **Scope:** only the configured repository. Other repositories are out of scope for MVP (D24).

**Acceptance criteria**
- AC1: A PR where I'm a required reviewer appears, marked Required, with my vote.
- AC2: A PR where I'm an optional reviewer appears, marked Optional.
- AC3: A PR where only my team is a reviewer appears, marked "via team".
- AC4: A PR where I'm not a reviewer doesn't appear.
- AC5: A PR I'm on both directly and via a team appears once, with my direct role.
- AC6: Votes match the web UI for each sandbox PR.

**Error states.** Shared table above. "Identity not a reviewer" isn't an error here, because the PR simply isn't listed. If a team query returns 403/404, skip that team, show "Some team assignments couldn't be loaded", and still show the rest.

**Test cases**
- Unit, fixture server:
  - union and de-duplication across the my-id and team-id responses;
  - role and vote mapping for votes 10, 5, 0, −5 and −10;
  - `hasDeclined` hiding;
  - a failed team query degrades without failing the list.
- Manual (S2): PRs A–C below, compared with the web UI's "Assigned to me" tab.

## F3. Reviewed marking (dismiss)

**User story.** When I've finished reviewing a PR I mark it reviewed, and it leaves my default list until it changes.

**Behaviour**
- **Actions:** "Mark as reviewed" and "Mark as not reviewed", in the list's context menu and on the details tab.
- **Recording:** marking stores the PR's **latest iteration** and that iteration's `sourceRefCommit`, fetched at the moment of marking with `GET {repo}/pullRequests/{id}/iterations`.
- **If the PR changed while I was looking:**
  - Condition: the latest iteration is newer than the one I last viewed (F4).
  - Show "This PR was updated since you opened it (iteration N → M)."
  - Offer: Mark anyway, or Review update.
- **Default lists** ("Assigned to me" and the main list) hide reviewed PRs. The filter "Show reviewed" brings them back.
- **Local only:** marking is not sent to Azure DevOps and doesn't change votes.
- **Any PR:** marking works whether or not I'm a reviewer. Votes are a separate, later feature.

**State model**

Stored in an application-level `PersistentStateComponent` file, `azure-devops-pr-review-reviews.xml`, never in the project, so it isn't committed. One record per key:

| Field | Type | Meaning |
|---|---|---|
| key | `{organization}/{repositoryId}/{pullRequestId}/{userId}` | Per user and PR. Using `repositoryId` (GUID) survives repo renames. `userId` keeps accounts separate. |
| reviewedIteration | Int? | Iteration id when marked reviewed; null = not reviewed |
| reviewedSourceCommit | String? | `sourceRefCommit` of `reviewedIteration` |
| lastViewedIteration | Int? | F4 |
| lastViewedSourceCommit | String? | F4 |
| lastViewedAt | Instant? | Informational only; **never used for comparisons** |

Records for PRs that are completed or abandoned and untouched for 90 days are pruned when the list loads.

**Acceptance criteria**
- AC1: A reviewed PR disappears from the default list immediately, and stays hidden after an IDE restart.
- AC2: "Show reviewed" lists it with a Reviewed badge.
- AC3: "Mark as not reviewed" returns it to the default list.
- AC4: Marks are separate per user and per organization.
- AC5: Nothing is written to Azure DevOps by marking. Check: the request log shows no write calls.

**Test cases**
- Unit:
  - marking stores the latest iteration and commit;
  - hide and show filtering;
  - per-user keys;
  - pruning;
  - the "updated while viewing" warning when latest > lastViewed.
- Manual (S3): mark PR D reviewed, restart the IDE, and check it's still hidden.

## F4. Update detection

**User story.** If a PR I marked reviewed gets new commits or a new iteration, it comes back to my list as needing review again.

**When "last viewed" is recorded.** On opening the PR's details or diff, after the iteration list has loaded: `lastViewedIteration` = the highest iteration id, and `lastViewedSourceCommit` = its `sourceRefCommit`. Only actually viewing the PR updates them. Refreshing the list doesn't.

**Clearing rule.** Compare against the stored iteration, never against time:

```
changed(pr) = latestIteration(pr) > reviewedIteration
           || latestSourceCommit(pr) != reviewedSourceCommit
if reviewedIteration != null && changed(pr):
    reviewedIteration = null; reviewedSourceCommit = null   // needs review again
    keep lastViewedIteration                                // F5 compares against it
```

**Signals**
- **Cheap check on every list load:** compare `lastMergeSourceCommit.commitId` from the list response with `reviewedSourceCommit`. It's already in the list response (verified), so it costs no extra call.
  - It's a proxy: it reflects the source commit of the last merge attempt and may lag while `mergeStatus` is `queued` (**UNVERIFIED** timing).
- **Authoritative check** when the cheap check differs, or when the details tab opens:
  - Call `GET …/iterations`.
  - Iteration ids increase by 1 per new iteration (verified: 1, 2).
  - New iterations come from push, force-push, rebase and retarget (`IterationReason` flags: push=0, forcePush=1, create=2, rebase=4, unknown=8, retarget=16, resolveConflicts=32; [IterationReason](https://learn.microsoft.com/en-us/javascript/api/azure-devops-extension-api/iterationreason)).
  - A retarget creates an iteration without a source-commit change. The rule above still clears the mark, which is intended because the diff base changed.
- **Never compared:** `lastMergeCommit`. It changes when the target branch moves, which would clear marks for changes the author didn't make.
- **Target-only advances:** whether they create an iteration is **UNVERIFIED** (sandbox S3 step 5).

**Acceptance criteria**
- AC1: PR marked reviewed at iteration 1, then a push creates iteration 2 → the next list load shows it as "Updated since review" in the default list.
- AC2: PR marked reviewed, then only a comment is added → it stays reviewed, because comments don't create iterations.
- AC3: PR marked reviewed, then a force-push or rebase → cleared, with the reason shown.
- AC4: Marked reviewed, then the target branch advances with no PR change → stays reviewed, unless the service created an iteration (record what happens).
- AC5: The comparison doesn't depend on the clock. Changing the system time doesn't change results.

**Test cases**
- Unit, pure function `changed(stored, latestIteration, latestSourceCommit)`:
  - same iteration and commit → false;
  - higher iteration → true;
  - same iteration, different commit → true;
  - no mark → no-op.
- Unit, fixture server: list response with a new `lastMergeSourceCommit` → one `iterations` call → mark cleared. Unchanged commit → no `iterations` call.
- Manual (S3): the push, comment-only, force-push and target-advance steps.

## F5. Update view ("what changed since I last looked")

**User story.** When a PR comes back as updated, I see exactly what's new since the iteration I last viewed, so I re-review only that.

**Shown** as a banner on the details tab and a badge in the list, e.g. "Updated: iteration 2 → 4":
- **Iterations since last view:** ids, dates and reasons (push, force-push, rebase, retarget).
- **New commits:**
  - `GET …/iterations/{latest}/commits` minus `GET …/iterations/{lastViewed}/commits`, by `commitId`.
  - The lists are cumulative (verified: iteration 2 returned 2 commits).
  - Paging uses `top`/`skip` with no `$`, max 500 per page ([iteration commits](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-commits/get-pull-request-iteration-commits?view=azure-devops-rest-7.1)).
- **Files changed since last view:**
  - `GET …/iterations/{latest}/changes?$compareTo={lastViewed}`. Verified to return only the delta: iteration 2 vs 1 gave 1 entry, `/src/Calculator.cs`.
  - **Show changes since last view** opens the diff chain over those files: left = `sourceRefCommit` of `lastViewed`, right = latest `sourceRefCommit`.
  - **Show all changes** keeps the normal merge-base diff.
- **Never viewed before:** no `lastViewedIteration` → no banner. The PR is simply "Needs review".

**Acceptance criteria**
- AC1: After a push of 1 commit touching 1 file, the banner shows "iteration N → N+1", 1 new commit and 1 file, and the "since last view" diff shows only that file.
- AC2: After 2 pushes, the banner shows both iterations and the union of their files.
- AC3: After a force-push or rebase, the banner shows the reason. Files come from `$compareTo`. Whether that delta includes changes brought in by the rebase from the target is **UNVERIFIED** (S3 step 4), so the result is recorded.
- AC4: Opening the PR updates `lastViewedIteration`, and the banner disappears on the next view.

**Test cases**
- Unit, fixture server: commit-set difference, `$compareTo` request parameters, banner text for 1 and for N iterations, no banner without `lastViewedIteration`.
- Recorded fixtures: iteration commits for sandbox PR 1, iterations 1 and 2.
- Manual (S3): steps 2–5.
